LOS 03

Multi-tenancy

One tenant id, in LOS and in Fineract.

LOS follows Fineract’s isolation model. One deployment serves many institutions. Each institution is a tenant with its own database. A request names that tenant and can see only that institution’s members, applications, and loans.

Tenant registryShared catalogue of tenant id and connection details. Applications and loans stay in the tenant database.
→
RequestHeader Fineract-Platform-TenantId. The tenant stays on the request for its whole life.
→
Tenant databaseLOS origination data, and the matching Fineract database for products, savings, and the loan.
Same identifier

kisumu-sacco is kisumu-sacco

The LOS tenant id is the Fineract tenant id. The disbursal call carries the id the officer signed in with.

Separate data

Origination stays inside the tenant

Leads, loan applications, borrowers, guarantors, documents, journeys, and rule versions live in that tenant’s LOS database. Each SACCO sees only its own queue.

One session

The branch screen is already scoped

Jane Achieng signs in to kisumu-sacco. Product setup, savings lookup, eligibility, and sanction all run against that tenant, on both sides of the handoff.

The primary entity is the loan application, loan_app_ref. A lead becomes that application. Borrowers, collateral, and guarantors attach as the journey progresses. Configurable data files add fields without a code change.

Audit

Every status change, rule run, document decision, and guarantee response is retained on the application.

LOS 09

Credit policy

Rules live in data, on a GoRules-compatible core.

LOS stores versioned JSON decision models per product. An open-source rule core compatible with GoRules evaluates facts and returns a decision. Officers change a multiple or a gate by publishing a new rule version, which keeps a full history.

Facts in, decision out

  • Qualifying savings balance and the product multiple
  • Requested amount and proposed disbursal amount
  • Eligible collateral value and guarantee cover
  • KYC and document completeness, and the current stage

The engine returns the maximum eligible amount, the guarantee still required, whether sanction is allowed, and the reasons the officer sees on screen.

ProductMultipleCollateral offsets guaranteeGuarantor stage

LOS 17

Integration

LOS reads Fineract products and writes the loan once.

Every Fineract call from LOS sends Fineract-Platform-TenantId. For this file the value is kisumu-sacco, so products, savings, the client, and the loan stay in that tenant’s database.

  1. 1GET/v1/loanproducts/{id} — terms the journey is allowed to offer
  2. 2GET/v1/savingsaccounts/{id} — qualifying balance at application and again at sanction
  3. 3POST/v1/clients — create a client, or link an existing client id
  4. 4POST/v1/loans — loan from the Fineract product, external id loan_app_ref
  5. 5POST/v1/loans/{loanId}/collaterals and /guarantors
  6. 6POST/v1/loans/{loanId}?command=approve then command=disburse

What stays a Fineract concern

  • Product catalogue, interest, schedule, charges, and accounting
  • holdGuaranteeFunds and mandatoryGuarantee as a fund hold on the live loan
  • Repayment, arrears, and close of business

Applied in LOS before the loan exists

  • A branch journey keyed by application status
  • A product rule for a savings multiple
  • Guarantor approve and reject before sanction
LOS 18

Acceptance

Three customer requests, checked on the file.

Each request is a product option, a rule the engine enforces, and a condition the officer can see.

1 · Savings multiple

Cap the loan from deposits

  • Product stores a multiple such as 2×, 3×, or 5×
  • Qualifying savings are read at application and at sanction
  • The maximum eligible amount blocks an oversized application
  • Disbursal cannot exceed that maximum
  • The rule is credit policy, and collateral is configured on its own
2 · Collateral offset

Optional reduction of the guarantee

  • Product flag: consider client collateral in the guarantor requirement
  • When on, eligible collateral is deducted from the amount to guarantee
  • Guarantors cover only the remainder
  • When off, collateral does not change the guarantee amount
3 · Guarantor consent

Approval and a live balance

  • Each guarantor can approve or reject the assigned request
  • Status is pending, approved, or rejected, and stays visible for audit
  • Screen shows total required, approved cover, and outstanding balance
  • Balances recalculate on approval, rejection, and allocation changes
  • Sanction waits until the outstanding balance is zero
  • A rejection is resolved by assigning another guarantor
  • Loans that do not require guarantors keep the existing sanction path
LOS 19

Delivery shape

Configuration first, then the Fineract adapter.

The origination service is a separate application. Fineract remains the system of record for the loan after disbursal.

Journey file

States, tasks, and who may move a product from one status to the next.

Form files

Fields and checklists for quick entry, borrower detail, collateral, and verification.

Rule packs

GoRules-compatible decision models, versioned per product.

Fineract adapter

Read products and savings. Create or link the client. Create, approve, and disburse the loan.

Phase 1

Open the file

Tenant registry aligned with Fineract, then the lead, loan application, quick entry, and the savings-multiple eligibility rule.

Phase 2

Complete the credit file

Detailed data, including collateral collection, verification, collateral offset, guarantor consent, and the guarantee balance.

Phase 3

Release the loan

Sanction gate, then the client, loan, collateral, guarantor, and disbursal calls into Fineract.
